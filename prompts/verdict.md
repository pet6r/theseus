# Phase 4 — Verdict + SOC action

**Goal:** Combine triage, capabilities, and IoCs into a single SOC-actionable verdict.

## Inputs

You have triage JSON, capabilities JSON, iocs JSON from previous phases.

## Scoring rubric

Compute `score` in [0.0, 1.0]:

- Start at `triage.suspicion_score / 100`.
- For each capability with confidence ≥ 0.7, add 0.05 (cap at 0.95).
- If 3+ network-category capabilities (T1071, T1573, T1090, etc), add 0.10.
- If injection + persistence + C2 all present, snap to ≥ 0.85.
- If packed AND no evident capabilities (i.e. analysis was thin), do NOT exceed 0.6; mark `unknown` instead of `malicious`.

## Label mapping

| Score | Label |
|-------|-------|
| < 0.20 | `clean` |
| 0.20 – 0.49 | `suspicious` |
| 0.50 – 0.94 | `malicious` |
| ≥ 0.50 but analysis incomplete (packed, etc) | `unknown` |
| (special — see below) | `vulnerable` |

### `vulnerable` — when to pick it

Use `vulnerable` for binaries that **expose offensive capability** but are not themselves performing malicious work. Typically:

- **Kernel drivers** exposing arbitrary kernel R/W, MSR access, physical memory mapping, or process-token swaps via IOCTL — even if the driver claims to be a legitimate product. This is the BYOVD ("bring your own vulnerable driver") category that attackers weaponize.
- **Legitimate signed software** with a documented exploitable flaw (e.g. a game anti-cheat or AV component shipping `MmMapIoSpaceEx`-style primitives).
- **Dual-use offensive tooling**: PoC drivers, exploit primitives, kernel debuggers without legitimate vendor identity.

Pick `vulnerable` over `malicious` when **the binary itself is not performing C2, exfil, or destructive action** — it only enables those when paired with userland code. Signal the SOC team to treat it as a weapon-grade primitive, not finished malware.

Indicators that push toward `vulnerable`:
- Driver creates `\Device\<name>` IOCTL surface AND handlers expose `ZwReadVirtualMemory` / `MmMapIoSpaceEx` / `PsLookupProcessByProcessId` + R/W
- Pattern-scan resolution of unexported kernel symbols (`MmPfnDatabase`, `EPROCESS` offsets)
- Driver is **unsigned or self-signed** yet ships kernel-exploitation primitives
- No network capability, no persistence, no obvious payload — just primitives

`vulnerable` score should be ≥ 0.70 (high-confidence weapon-grade primitive).

## SOC action mapping

| Label | Action |
|-------|--------|
| clean | `ignore` |
| suspicious | `enrich` (push to threat intel for context) or `monitor` |
| malicious | `quarantine` if endpoint flagged it, else `escalate` |
| vulnerable | `quarantine` (block driver load) + `escalate` (BYOVD weapon on endpoint = incident) |
| unknown | `escalate` to a human analyst |

## YARA rule (optional, include if confident)

Generate a minimal YARA rule from:
- 2-3 highest-xref unique strings (avoid generic strings)
- 1-2 import name combinations
- file format/arch

Example:

```yara
rule theseus_<sha8>_<verb> {
    meta:
        description = "Auto-generated by Theseus"
        verdict = "malicious"
    strings:
        $s1 = "http://c2.example.com/beacon" ascii
        $s2 = "Global\\\\theseusmtx_42" ascii
    condition:
        uint16(0) == 0x5A4D and 2 of ($s*)
}
```

Skip YARA if confidence < 0.6 or strings are too generic.
